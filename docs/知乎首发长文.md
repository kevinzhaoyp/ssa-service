# 客户只给 1 台服务器，我的微服务变成了灾难

> 一个后端老兵的踩坑自白，以及我后来造的「反微服务」框架

---

## 一、那个让我怀疑人生的下午

2019 年下半年，微服务火得离谱。火到什么程度？不用就好像你落后了，不管系统大小、不管客户能提供什么服务器，都得上微服务。

我当时也没忍住。找了前大厂同事、一位 Java 高手，帮我搭了一套微服务架构，兴冲冲一头扎进去。一开始为「业务怎么拆」就头疼，没多久拆出好几个微服务 —— 可业务还没写完呢。

然后现实给了我一巴掌：**客户只给 1~2 台服务器。**

数据库、Redis、Nacos……各种中间件一跑起来，资源就没了。要把所有微服务都跑起来？那是灾难。再加上各种运维工具不起、日志满天飞、还不好找。

那一刻我彻底清醒：**微服务不是银弹，轻量才是大多数项目的真相。**

---

## 二、被写死 SQL 折磨出来的念头

说回更早。2019 年我转 Java，接手了一套底层用 JFinal 的「很烂的系统」。里面**全是写死的 SQL**，加个字段、改个字段都是灾难。我维护了一两个月，就开始想：怎么让自己轻松点？

于是我把这些 SQL 写成**模板放到外面，热加载进来** —— 小问题谁都能改，改好告诉我，我来合并。

这个朴素的念头，后来长成了我今天要说的框架：**SSA Service**。

---

## 三、SSA Service：平台无业务，一切皆插件

它的内核**没有任何业务**，只负责：接收请求 → 找插件里的接口 → 执行 → 返回。业务 100% 写在「动态插件 JAR」里，需要就挂、不需要就卸载，**平台永远不碰逻辑**。

自研 `SpringMvcPluginClassLoader`（继承 `URLClassLoader`）运行时扫描插件 jar，把标注类注册成 Spring Bean、按 `routePrefix` 挂路由；支持 `enablePlugin/disablePlugin` **运行时热启停**，坏插件不拖垮启动。

### 写一份 YML = 一个接口

```yaml
key: user-list
datasource: main
content: |
  SELECT id, name, email FROM ssa_user WHERE status = #{status}
params2:
  - name: status
    type: int
    required: 1
returnType: list
```

不用写 Controller、不用写 Service，`POST /sqlApi/v1/user/list` 就能调。

### 注解即 API，且能覆盖 YML（MethodApi）

```java
@SsaApiClass("report")
public class ReportApi {
    @SsaApiMethod(name = "profit")   // 同名时覆盖 sql-api
    public Object profit(Map params) { return ...; }
}
```

先用 YML 跑通 80%，复杂逻辑写同名方法无缝覆盖（「代码级逃生舱」）。

## 四、最让我兴奋的一点：它接上了 AI

因为每项能力都是统一 HTTP API，末尾加一行 `mcptool:true`，接口就**自动注册成 MCP 工具**（基于官方 MCP Java SDK 2.x，Streamable HTTP；`POST /mcp/rescan` 热刷新；调用走同进程，零网络跳）。

于是你原先在后台里一个个点的操作 —— 「把 X 客户账期改到 90 天」「导出发票台账发给财务」 —— 现在智能体（WorkBuddy 等）能用自然语言直接驱动。**一套声明，前端 / CLI / Agent 三端复用。** 已经和 WorkBuddy 打通。

> 这正是当下 AI Agent 最缺的「最后一公里」：把存量系统的能力，零重写地暴露给智能体。

---

## 五、一体多态：同一套代码，三种形态随便切

同一套插件 JAR，可在 **单体 `ssa-ser` / 嵌入式 `ssa-ser-client` / 微服务 `ssa-msa`（Gateway+Nacos+N×ssa-ser）** 间**零改动切换**。我称之为 **一体多态 · Fluid Topology**—— 小项目单 JAR 起步，业务涨了加网关注册多实例即可水平扩展。像水没有固定形状，却能装进任何容器。
